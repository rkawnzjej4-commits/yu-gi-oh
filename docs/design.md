# 설계 제안

## 변경하지 않을 기준

- 카드 포함 자격은 일본 OCG 최초 발매일 `<= 2012-03-31`이다. 재록일, 한국·TCG 발매일, 테마 등장 연도로 대체하지 않는다.
- 듀얼은 개발 시 확인한 현행 OCG 규칙, 최신 공식 텍스트·에라타·재정으로 처리한다. 2012년 규칙 모드를 선택하지 않는다.
- 한 카드의 효과 일부만 구현한 상태로 플레이에 넣지 않는다. 미지원 카드는 보상·상점·스타터·적 덱 모두에서 제외한다.
- 로그라이크는 듀얼 밖에 적용한다. 보스도 동일한 듀얼 규칙과 확정된 덱 규정을 따른다.

## 엔진 선택

**우선 제안: Project Ignis/EDOPro의 ocgcore와 호환되는 CardScripts를 고정 버전으로 도입한다.** 공식 엔진은 아니므로 공식 OCG 자료를 정답으로 한 별도 회귀 검증이 필요하다. 최신 브랜치를 받았다는 사실만으로 현행 OCG 준수를 선언하지 않는다.

| 선택지 | 장점 | 핵심 비용·판단 |
| --- | --- | --- |
| ocgcore + 호환 Lua 스크립트 + 새 클라이언트 | 소환·체인·전투·효과 상태 기계를 재사용하고 로그라이크 UI를 자유롭게 구성 | 메시지 프로토콜, 카드 DB, 선택 UI, AI 연결을 직접 구현해야 함. 제품 구조의 우선 후보 |
| EDOPro 클라이언트 포크 | 기존 듀얼 UI와 프로토콜 구현을 재사용, 비교 검증에 유용 | 기존 C++ 클라이언트 구조에 로그라이크를 통합해야 함. 새 UI 연결 비용이 크면 대안 |
| 규칙·효과 엔진 자체 작성 | 모든 구조를 직접 통제 | 타이밍·재정·다수 카드 상호작용 비용이 매우 큼. 첫 프로토타입에는 권장하지 않음 |

ocgcore는 독립 라이브러리로 빌드 가능하고 C API 및 Lua 실행기를 제공한다. 조사한 API 헤더와 README에는 함수 인자 표기 차이도 있다. **선택한 커밋의 헤더를 실제 계약으로 사용**하고, core/API 버전·스크립트·공용 Lua 헬퍼·카드 DB를 하나의 호환 묶음으로 고정한다. 스크립트를 카드별로 복사해 헬퍼 없이 실행하지 않는다.

엔진·클라이언트·CardScripts는 조사 당시 AGPL-3.0-or-later를 명시한다. 도입 시 고지·소스 제공 등 의무를 확인하고 프로젝트 배포 방식을 정한다. 비상업적이라는 조건만으로 카드 이미지·텍스트·상표의 이용 허락이 생기는 것은 아니다. 초기 화면은 텍스트와 자체 제작 자리표시자로 구성하고 배포 자산의 권리는 별도로 확인한다. 프로세스 분리를 라이선스 회피 수단으로 취급하지 않는다.

## 권장 실행 구조 — 아직 채택·구현 전

초기 대상은 **로컬 싱글플레이 데스크톱**. 클라우드에서는 Linux 헤드리스 검증을 우선하고, Windows 배포와 UI 검증은 별도 단계로 둔다. 브라우저/WASM·모바일 이식은 첫 목표에서 제외한다.

```text
로그라이크 상태 / UI (Godot 4 + GDScript 후보)
        ↕ 버전 있는 명령·이벤트
듀얼 어댑터 / 로컬 worker (C++17 이상)
        ↕ 고정한 C API
ocgcore + 호환 Lua 스크립트 + 엔진용 카드 데이터

검증된 카드 카탈로그 → 스타터 / 보상 / 상점 / 적 덱 / 덱 검증
AI → 플레이어와 동일한 합법 선택 인터페이스 → 듀얼 어댑터
```

첫 엔진 검증은 C++ CLI로 수행한다. 통과 후 Godot와 로컬 worker를 연결하는 작은 시험으로 UI 선택을 확정한다. 추가 프로세스가 부담이면 같은 인터페이스를 네이티브 확장으로 옮길 수 있다. UI 작업 전에 외부 프로세스 관리·종료·패킷 경계·프로토콜 버전을 검증한다.

엔진을 게임 상태의 단일 판정자로 둔다. UI/AI가 소환 가능 여부나 효과 계산을 별도로 추측하지 않는다. 어댑터는 엔진의 바이너리 메시지를 길이·타입 검사 후 안전한 구조로 변환한다. 선택마다 `duel_id`, `request_id`, `actor`, 후보와 제약을 부여하며 오래된 응답·중복 응답을 거부한다. 카드·위치·수량·순서·효과·체인·공격·합계·예/아니오 등 **선택 카드 풀에서 발생 가능한 모든 프롬프트**를 처리해야 한다. 알 수 없는 메시지를 자동 패스하지 말고 진단 로그와 함께 중단한다.

현행 OCG 옵션은 엔진에서 명시적으로 지정하고 실제 값과 근거를 저장한다. 기본값에 의존하지 않는다. 규칙 검사 대상에는 첫 턴 드로우/공격, 우선권과 체인 창, 스펠 스피드, 동시 유발 효과, 데미지 스텝, 비용과 대상, 무효·불발·파괴 구별, 공개·비공개 위치 이동, 엑스트라 덱 소환 위치가 포함된다. 모든 합법적 카드에 동일한 규칙을 적용한다. 과거 카드 풀에 펜듈럼·링크 카드가 없다는 사실은 과거 마스터 룰을 사용한다는 뜻이 아니다.

최신 텍스트는 표시용 문자열만 교체해서는 안 된다. 수치·종족·속성·종류·별칭·카드군 등 엔진 데이터와 Lua 동작도 공식 내용에 맞아야 한다. OCG와 TCG가 다른 재정은 OCG 근거로 검증하고, 충돌하면 해당 카드를 보류한다.

## AI는 별도 개발 항목

ocgcore를 붙여도 상대 AI가 생기지 않는다. WindBot Ignite는 EDOPro 방 프로토콜에 접속하며 덱별 executor가 필요하다. C API에 직접 연결되는 범용 AI로 가정하지 않는다. 기존 executor와 덱에는 기준일 이후 카드가 있을 수 있다.

처음에는 모든 프롬프트에 합법 응답을 제공하는 테스트용 정책으로 엔진 연결을 검증한다. 플레이용 최소 AI는 한 개의 검증된 적 덱에 대해 소환·효과·공격·체인·대상 선택의 휴리스틱을 작성한다. 이후 세 스타터와 보스 덱에 맞춰 확장한다. 단순한 판단은 허용하지만 규칙 생략은 허용하지 않는다. 상대 손패·덱 순서를 AI에 노출하지 않으며 자기 손패와 공개 정보로 판단하게 한다. 고정 시드 회귀 테스트는 가능하되 실제 게임의 AI가 덱 순서를 시드에서 복원하지 않도록 한다.

## 단계별 최소 범위와 완료 조건

일정은 아직 추정하지 않는다. 아래 카드 수는 검증 비용을 제한하기 위한 목표 범위이고 확정 명단이 아니다.

| 단계 | 만드는 것 | 완료 조건 |
| --- | --- | --- |
| M0 엔진 적합성 시험 | core 빌드, C++ CLI 어댑터, 12–20종의 검증 후보, 재현 가능한 테스트 장면 | 정상 소환·체인·전투·묘지 효과·무효·대표 싱크로/엑시즈 상호작용의 기대 결과 검증. 공식 근거와 맞지 않으면 채택 보류 |
| M1 첫 완주 가능한 듀얼 | 약 24–40종을 공유하는 플레이어 덱 1개와 적 덱 1개, 기본 UI, 최소 AI | 덱은 각각 합법적인 메인 40장으로 구성. 모든 선택 UI 지원, 정상 승패·드로우 불가·기권 처리, 미지원 메시지 0건, 여러 고정 시드에서 실제 듀얼 종료 |
| M2 로그라이크 수직 구현 | 스타터 3종, 지역 1개, 보스 1명, 약 40–60종의 검증된 카드, 저장 | 시작→분기→일반 듀얼→보상/상점/이벤트→덱 편집→보스→승리 또는 패배 종료를 끝까지 검증 |

M0의 소수 카드 장면은 규칙 검증용이며 합법적인 완성 덱이나 플레이 가능한 게임이라고 부르지 않는다. 목표 수량이 부족하면 검증된 카드 수를 늘려 합법적인 덱을 구성한다. 금지·제한 카드를 임의로 추가하거나 같은 카드를 3장 초과해 넣어 수량을 맞추지 않는다.

스타터 후보는 **일반/어드밴스 비트다운, 싱크로 전개, 랭크 4 엑시즈**로 잡는다. 명칭과 실제 덱은 발매일·최신 효과·금제 검증 후 확정한다. 3개 덱은 검증된 범용 카드를 공유해 구현량을 줄인다. 의식·융합 등 아직 다루지 않은 카드의 추가는 별도 검증 단계로 진행한다. 선택한 카드의 일부 효과가 의식·융합 등을 요구한다면 그 처리까지 검증하거나 카드 전체를 보류한다.

M2 지도는 예를 들어 6개 층의 작은 DAG로 구성하고 보스 도달 경로를 보장한다. 보상은 자격·지원·금제 필터 후 기존 덱과의 카드군/역할 연계 가중치로 3개 후보를 제안한다. 반복 금지·후보 부족 시 대체 재화 또는 건너뛰기를 제공한다. 필터를 무시한 카드로 빈칸을 채우지 않는다. 소유 수량과 덱 투입 수량은 별개다.

상점은 카드 구매, 이벤트는 재화·카드 획득/교환부터 구현한다. 이벤트로 유일한 합법 덱이 파괴되지 않도록 변경 후 출전 가능성을 검사한다. 듀얼 사이 HP 유지는 첫 버전에서 하지 않고 매 듀얼 LP 8000으로 시작한다. 매치/사이드 교체는 제외한 단판 듀얼이다. 승리 보상 전·후와 분기 선택 후 원자적으로 저장하며, 패배 시 도전을 종료한다. 기술 오류는 패배로 판정하지 않고 직전 안전 저장으로 복구한다. 듀얼 중 저장은 초기 범위 밖이다.

## 금지·제한 정책

아직 미확정이다. `banlist_policy`를 카드 발매 자격·구현 지원과 별도로 둔다. 추천 기본값은 검증된 현행 OCG 금제 스냅샷이며 `effective_from`, `verified_at`, 공식 출처, 카드별 최대 장수와 해시를 기록한다. 이를 아직 확보하지 않았으므로 현재 유효한 금제라고 주장하지 않는다.

로그라이크 전용 정책을 선택하면 명시적인 별도 프로필로 제공하고 변경 내용을 표시한다. 미설정 상태에서 무제한 프로필로 자동 대체하지 않는다. 이름을 동일하게 취급하는 카드 등의 합산 장수 제한과 메인/엑스트라 총량도 덱 검증기에 반영해야 한다. 이 덱 검증기는 현재 구현되지 않았다.

## 검증·재현·업데이트

런 시작 시 카드 풀, 규칙·공식 텍스트 확인 시점, 금제, core/스크립트/헬퍼/DB 해시, 시드, 게임 버전을 고정한다. 진행 중인 런에 최신 데이터를 자동 주입하지 않는다. 업데이트는 공식 재확인→변경 카드와 상호작용 회귀→새 스냅샷 발행 순서다. 규칙이 달라진 구버전 런은 보존된 실행 묶음으로 계속하거나 명시적으로 종료/이관한다. 조용히 혼합하지 않는다.

각 효과 테스트는 초기 영역·LP·턴/페이즈·입력 순서·예상 체인·최종 상태를 기록한다. 정상 효과뿐 아니라 발동 불가, 대상 소실, 코스트 지불 후 무효, 타이밍 차이도 포함한다. 에라타가 알려진 과거 카드, 일본/TCG 최초 발매가 다른 카드, 기준일 경계, 오래된 카드의 늦은 재록을 데이터 회귀 사례로 추가한다. 실제 카드 이름과 정답은 공식 근거 확보 전 만들어 넣지 않는다.

단위 테스트, 효과 장면 테스트, AI 완주, UI 선택 테스트, 재시작·세이브 복구를 구별해 결과를 남긴다. EDOPro와의 동작 비교는 연결 오류를 찾는 데 유용하지만 같은 core를 쓰므로 공식 재정의 독립적인 정답 검증을 대신하지 못한다.

## 다음 개발 순서

1. 공식 DB 및 공식 규칙·재정 자료 접근을 확보하고 확인 날짜를 기록한다.
2. core·CardScripts·헬퍼·DB의 호환 커밋과 라이선스를 확인해 외부 의존성 명세를 만든다.
3. M0를 빌드해 프로토콜·규칙 옵션·효과 회귀 시험을 수행한다.
4. 통과한 카드로 M1의 실제 덱을 확정하고 UI/AI를 연결한다.
5. M1 완주 후 세 스타터와 로그라이크 콘텐츠로 확장한다.

현재 완료된 것은 설계와 카드 카탈로그의 보수적 판정 도구다. 엔진 빌드·듀얼·카드 효과 검증은 아직 실행하지 않았다.
